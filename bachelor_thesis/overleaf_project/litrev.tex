\chapter{Literature Review}
\label{chap:litrev}

This chapter reviews the research that motivates and informs this study. It
is organised into six thematic sections: the emergence and definition of AI
coding agents (Section~\ref{sec:lr:agents}); empirical studies of adoption
rates on GitHub (Section~\ref{sec:lr:adoption}); detection methodology and
the multi-signal challenge (Section~\ref{sec:lr:detection}); how developers
interact with AI tools (Section~\ref{sec:lr:interaction}); the JavaScript,
TypeScript, and npm ecosystem as a research subject
(Section~\ref{sec:lr:ecosystem}); and the geographic dimension of
open-source software development and AI tool adoption
(Section~\ref{sec:lr:geography}). The chapter ends by identifying the
research gaps that this thesis addresses (Section~\ref{sec:lr:gaps}).

% ------------------------------------------------------------
\section{AI Coding Agents: Emergence and Definitions}
\label{sec:lr:agents}
% ------------------------------------------------------------

A \emph{coding agent} is an AI system that works in a loop: it plans a task,
takes an action such as writing code, running tests, or reading documentation,
observes the result, and repeats until the task is done~\cite{robbesAgenticMuch2026}.
This differs from an AI coding \emph{assistant}, which only provides suggestions
that the developer must accept one at a time. The distinction matters practically:
an assistant leaves a trace only when a suggestion is accepted, while an agent can
write entire functions, create tests, and open pull requests autonomously, leaving
a wider variety of observable traces in the repository history.

The technical foundation for today's agentic tools was established by Chen et
al.~\cite{chen2021codex}, who introduced Codex, a large language model fine-tuned
on 54 million public GitHub repositories and evaluated on HumanEval, a benchmark
of 164 hand-written Python programming problems. Their approach trained GPT-based
models on code corpora and measured pass@k rates (the probability that at least one
of $k$ generated solutions is correct). The best model solved 28.8\% of problems
in a single sample and 72.3\% with 100 samples. This was the first demonstration
that LLMs trained on code could produce functionally correct solutions rather than
merely plausible-looking fragments, and it became the technical basis for GitHub
Copilot. Its main value lies in establishing the first systematic benchmark for
LLM code generation and showing that production deployment was plausible at scale.
HumanEval is, however, almost entirely short self-contained Python functions; it
doesn't come close to representing multi-file projects with existing conventions,
test suites, and dependencies. Critics have further noted that many HumanEval
problems appear in the training corpus, so the benchmark may partly measure
memorisation. The memorisation concern is real, but it doesn't fully undermine the
result: Ziegler et al.~\cite{ziegler2022} found a 27\% suggestion acceptance rate
across 2,631 GitHub Copilot users in genuine production contexts, which wouldn't be
observed if the model merely memorised training examples.

Chatlatanagulchai et al.~\cite{chatlatanagulchai2025} conducted an empirical study
of \emph{context files} for AI coding agents, examining the prevalence, content, and
characteristics of files such as \texttt{CLAUDE.md}, \texttt{.cursorrules}, and
\texttt{AGENTS.md} across public GitHub repositories. Their approach combined
automated repository mining with content analysis of the instructions developers
write for agents. They documented rapid growth in the number of repositories
containing such files and found that their contents predominantly consist of
natural-language instructions about coding conventions, project structure, and
testing requirements. What sets this work apart is that it's the first systematic
characterisation of how developers configure agents at the project level, going
beyond the binary question of whether a file exists. The gap it doesn't address is
whether the agent actually follows those instructions, or whether the file was
created experimentally and then abandoned. That concern has real bite: Robbes et
al.~\cite{robbesAgenticMuch2026} found that \texttt{AGENTS.md}, originally Codex's
guidance file, is now used by more than 24 agents and can't reliably identify which
one is being configured, suggesting many context files are copied between projects
as boilerplate rather than authored as project-specific instructions.

Galster et al.~\cite{galsterConfig2026} carried out an empirical study of
configuration artifacts across 4,738 open-source GitHub repositories that contain
at least one known agent configuration file. They found 148,519 AI-co-authored
commits and 15,591 configuration files in their corpus, with TypeScript as the most
common primary language at 24.5\% of repositories. What this work does well is connect
the presence of configuration files to commit-level evidence of agent activity, giving
a more grounded characterisation than file presence alone. Its main limitation is
corpus scope: by seeding on repositories with configuration files, it captures only
the most explicitly configured subset of agentic development. Repositories that use
agents through commit trailers or PR markers without any configuration file simply
aren't there. Khosravani and Mockus~\cite{khosravani2026} found that
configuration-file signals alone detect up to 30 times less AI usage than a full
four-signal approach, so this population is a small and systematically
unrepresentative fraction of all AI-assisted development.

In a companion exploratory study, Galster et al.~\cite{galsterExploratory2026}
examined how practitioners configure agentic AI coding tools in open-source projects,
moving from the descriptive characterisation of configuration artifacts to an analysis
of the practices and patterns behind those configurations. The study covers multiple
ecosystems and configuration styles in a single analysis, which is its main
contribution. Exploratory studies are hypothesis-generating by design, so the patterns
reported are tendencies in the studied sample rather than definitive characterisations.
More importantly, the sample itself is a filtered subset: Robbes et al.~\cite{robbesAgenticMuch2026}
found that the gap between narrow and broad heuristic sets reaches 6.46 percentage
points on the same corpus, meaning the configuration practices Galster et al.\ observe
may differ substantially from those of the broader population of agent users who
adopt less explicitly.

Denisov-Blanch et al.~\cite{denisovBlanch2026} introduced RAMP (Repository AI
Maturity Profile), a four-level framework measuring how systematically a project
commits AI configuration artifacts to version control, ranging from basic behavioural
rules up to multi-agent orchestration. They applied observational panel analysis to
441 repositories stratified by RAMP level, comparing velocity and software quality
metrics before and after agent adoption; independent human validation achieved 97\%
accuracy on held-out samples. The findings are striking in two ways. Development
velocity increased consistently (28--38\% more commits) across all RAMP levels. But
quality outcomes diverged: repositories without committed AI configuration showed
roughly double the cognitive complexity increase and $1.7\times$ more static-analysis
warnings relative to those with committed configuration. The study also documents
that 73.8\% of configuration artifacts were committed once and never updated, a
``set-and-forget'' pattern that prevails even among projects at higher maturity
levels.

The RAMP framework is the main contribution here: it turns configuration maturity
into a reproducible, operationalisable measure and directly links committed
configuration to downstream quality outcomes, moving the question beyond whether a
configuration file exists to how systematically it is maintained. The observational
design is a limitation, since projects that commit AI configuration may differ from
those that don't in team discipline and broader engineering practices, meaning the
quality advantage could partly be a confound. The ``set-and-forget'' finding, though,
makes a purely disciplinary explanation hard to sustain: if the quality benefit were
driven by generally more disciplined teams, one would expect those teams to also
update their configuration regularly, yet static configuration is still associated
with lower quality costs.

Agarwal, He, and Vasilescu~\cite{agarwal2026} conducted a longitudinal study
distinguishing between AI IDEs (editor-integrated tools such as Cursor and
Windsurf) and autonomous coding agents (tools that complete full tasks with minimal
developer input). They tracked developer activity logs and repository metrics over
time to estimate the causal effect of each tool category on productivity and code
quality. Velocity gains from autonomous agents only materialise when the agent is
the first AI tool adopted in a project. Agent overuse produces an 18--39\%
quality degradation measured by post-merge bug rates. The longitudinal causal design
is what makes this study worth citing; most work in this space can only report
correlations. The limitation is that the sample relies on developers who consented
to telemetry collection, who may be more engaged or technically sophisticated than
average, potentially biasing toward stronger productivity effects. The ``agent first''
finding may also reflect a selection effect: projects that adopt agents before IDEs
tend to be newer and less technically complex, and those properties could
independently produce better velocity outcomes.

The key tools covered by this study and their approximate launch dates are listed
in Table~\ref{tab:tools}. The most important for the npm ecosystem is Claude Code
(launched March 2025), which targets developers who work in the terminal and by
default adds a \texttt{Co-Authored-By: Claude <noreply@anthropic.com>} trailer to
every commit it authors~\cite{robbesHeuristics2026}. This default behaviour makes
Claude Code the most straightforwardly detectable agent in repository mining studies.

point at which this study considers the ecosystem to have reached broad mainstream
availability, with several independent mature tools in active use and Claude Code
weeks from its public launch.

\section{Empirical Studies of Coding Agent Adoption}
\label{sec:lr:adoption}
% ------------------------------------------------------------

The two most comprehensive empirical studies of coding agent adoption on GitHub
are the \emph{Agentic Much?}~\cite{robbesAgenticMuch2026} and \emph{Agentic
Very Much!}~\cite{robbesAgenticVery2026} papers by Robbes et al. Together they
provide the baseline adoption rates against which this thesis measures the
JavaScript/TypeScript ecosystem.

\subsection{Adoption in Established Repositories}

Robbes et al.~\cite{robbesAgenticMuch2026} studied 128,018 GitHub repositories
across all programming languages using a data snapshot from 21 February 2026.
Their approach applied a taxonomy of 196 heuristics covering 63 AI coding
agents, classifying each repository as agentic, AI-assisted, or non-AI-assisted
based on the signals found. The study found an overall adoption rate of
22.20\% using a narrow heuristic set and 28.66\% using the full set; the
6.46 percentage-point gap represents repositories that are missed when fewer
signals are used, which is the undercounting delta that this thesis measures
for the JS/TS ecosystem. Additional findings include that AI-generated commits
are approximately three times larger than human commits (median 31 vs.\ 11 added
lines), and that the most common AI-assisted task type is feature work (35.7\%),
followed by bug fixing (29.9\%).

The scale here is what matters: 128,018 repositories and 196 heuristics across
63 agents is by far the most comprehensive catalogue in the literature. The
central limitation is that pooling all GitHub languages conflates high-adoption
ecosystems such as npm with low-adoption ones such as legacy C repositories, making
it impossible to determine whether the 22--28\% figure is high or low for any
specific technical community. The companion study~\cite{robbesAgenticVery2026}
makes this worse: adoption in new projects reaches 71--76\%, meaning the
pooled average obscures a fundamental cohort effect and may be unrepresentative
of any real sub-population.

\subsection{Adoption in New Repositories}

A companion study~\cite{robbesAgenticVery2026} focused specifically on 12,794
repositories \emph{created} after 29 August 2025, the point the authors identify
as the maturation of the agentic AI era, applying the same heuristic taxonomy.
The results are striking: adoption in new repositories reaches 71.83--76.15\%,
roughly three times the rate in established repositories. The median fraction of
AI-authored commits is approximately 30\% in new repositories versus 10\% in older
ones, and repositories where agents contribute to more than half of all commits
rose from 21.1\% in older projects to 41.2\% in new ones. Claude Code accounts
for approximately three times more signals than Copilot in new repositories,
consistent with its terminal-first design that fits naturally into npm workflows.

The key contribution is demonstrating that new projects adopt agents at qualitatively
different rates from established ones, which directly motivates the corpus
construction date threshold used in this thesis. The corpus of new repositories is
small relative to all GitHub projects, though, and the quality filters applied
(at least 10 stars, 5,000 lines of code, 100 commits) may oversample highly active
new projects where agent adoption would be expected to be highest. Agarwal et
al.~\cite{agarwal2026} found that agents rapidly increase both commit count and code
volume, making it easier for agent-heavy projects to meet those activity thresholds.
That would artificially inflate the measured adoption rate among qualifying repositories,
independently of the selection on new projects.

\subsection{A Census of All GitHub Repositories}

Khosravani and Mockus~\cite{khosravani2026} conducted the largest analysis of
AI-assisted software development to date, scanning over 180 million public GitHub
repositories across all languages and time periods. Their approach applied four
complementary detection signals: registered AI bot account authorship, commit
message trailers, author email patterns, and configuration file presence. The
central finding is that detecting only one signal, specifically registered bot
accounts, misses up to 30 times the AI usage detected by the full four-signal
approach. This is the clearest quantitative evidence in the existing literature
that single-signal detection fundamentally undercounts adoption. The study also
estimates over 320,000 AI-authored commits per month on GitHub as of early 2026,
confirming that agent use has moved from experimental to routine.

The principal strength is comprehensiveness: 180 million repositories avoids the
corpus selection bias inherent in filtered studies. The flip side is that scanning
all repositories, including abandoned projects and toy repositories, likely deflates
the adoption rate relative to studies that restrict to active, maintained projects.
Kalliamvakou et al.~\cite{kalliamvakou2016} documented that a substantial fraction
of GitHub repositories are experimental or non-genuine, and if AI tools
disproportionately generate throwaway projects, the 180-million-repository denominator
may itself include a large number of AI-created repositories classified as inactive,
paradoxically suppressing the measured rate even while those repositories constitute
evidence of AI use.

\subsection{Early Adoption Patterns}

Raida and Hou~\cite{raida2026} studied the early adoption phase of agentic coding
tools by analysing 25,264 pull requests from 2,361 GitHub repositories, characterising
project-level adoption intensity and the human--agent collaboration models that emerged
during this period. Their approach identified agentic PRs across repositories and
measured productivity proxies (PRs per participant per quarter) alongside
collaboration structure metrics. The study documents concentrated rather than
widespread adoption: the median repository generated only one to two agentic PRs
over a three-month window, well below an industry benchmark of 36 PRs per participant
per quarter. Smaller projects with one to five contributors showed higher participation
rates with agentic tools than medium and large projects. The dominant collaboration
model was a single-human oversight pattern, in which one developer reviews and
optionally modifies the agent's output before merging, with multi-developer review
remaining rare.

The project-level unit of analysis is what distinguishes this work from most of the
literature: it captures intensity and collaboration structure rather than simply
whether a repository has ever used an agent. The limitation is that the corpus is
restricted to repositories with identifiable agentic PRs, which represent the most
visibly committed adopters. Repositories where agents were used without leaving
explicit PR-level signals are absent entirely. The low median intensity of one to two
agentic PRs may therefore reflect detection gaps rather than genuinely low usage:
Khosravani and Mockus~\cite{khosravani2026} found that single-signal detection misses
up to 30 times the AI activity captured by a full multi-signal approach.

\section{Detection Methodology and the Multi-Signal Challenge}
\label{sec:lr:detection}
% ------------------------------------------------------------

Answering the question ``does this repository use AI coding agents?'' requires
observable signals left in the repository's public record. The literature
converges on four main signal families~\cite{robbesHeuristics2026,
galsterConfig2026, khosravani2026}.

Robbes et al.~\cite{robbesHeuristics2026} published a dedicated catalogue of
heuristics for detecting AI-generated commits on GitHub, covering 63 AI coding
agents with 196 individual detection signals catalogued from agent documentation,
known default behaviours, and manual inspection of agent-generated commits. Key
findings from applying this catalogue at scale include 2.7 million commits
carrying the Claude Code authorship email (\texttt{noreply@anthropic.com}) and
2.1 million pull request branches with the \texttt{codex/} prefix. The breadth
here is the main contribution: by systematically cataloguing signals for 63 agents
rather than the 3--5 covered in most prior work, it captures a far larger fraction
of the true adoption signal. Heuristics are static, though, and may become outdated
as agents change their default behaviours; they're also deliberately vulnerable to
developers who modify commit trailers to conceal or simulate agent use.
Ghaleb~\cite{ghaleb2026} demonstrated that individual agents leave distinguishable
fingerprints in repository structure and commit metadata beyond the patterns captured
in standardised heuristic catalogues, suggesting that the coverage of any fixed
catalogue will erode over time as agents diversify their observable behaviours.
Attribution approaches capable of identifying \emph{which} agent was used represent
a complementary methodology rather than a full substitute.

Dey et al.~\cite{dey2020biman} introduced BIMAN, a systematic framework for
detecting bots in GitHub commit and issue comment histories, predating the
emergence of AI coding agents. Their approach combined four complementary signals:
author name pattern matching, commit message pattern analysis, file modification
pattern analysis, and project association graphs. Evaluating on a manually labelled
ground truth, they found that 7.3\% of GitHub committers are bots and that bot
commits constitute a disproportionately large share of total commit volume due to
CI/CD automation and dependency-update services. The interpretable multi-signal
design is its main value: analysts can understand why an account was flagged rather
than treating the decision as a black box. The fundamental limitation for this
thesis's purposes is that BIMAN was designed to detect CI/CD bots rather than AI
coding agents. AI agents are intentionally designed to produce human-like commit
patterns that the original BIMAN signals weren't calibrated to detect, so detection
frameworks purpose-built for AI agents are needed alongside bot-detection tools.

Ghaleb~\cite{ghaleb2026} addressed the problem of attributing repository contributions
to specific AI coding agents, going beyond the binary question of whether AI was
used to the finer-grained question of which agent was responsible. Participating in
the MSR 2026 Mining Challenge, their approach analysed observable patterns in GitHub
repositories to fingerprint agent-specific contributions, using the distinctive
traces that different agents leave in commit metadata, branch naming conventions, and
repository structure. The focus on agent-level attribution is more informative than
binary AI/human classification and directly supports the kind of tool-specific
adoption counts reported in this thesis. A fundamental limitation is that
fingerprinting approaches calibrated on a challenge dataset may not generalise to
corpora assembled with different sampling criteria. As AI agents are trained on
human feedback to produce more uniform-looking output, the agent-specific features
that fingerprinting relies on may converge across tools, reducing discriminative
power as observable differences between agents shrink.

Cynthia, Das, and Roy~\cite{cynthia2026} conducted a large-scale study of coding
agent usage patterns on GitHub, examining how core and peripheral contributors
differ in their use of AI coding agents and whether usage patterns vary
systematically across contributor roles and project types. Their approach combined
multi-signal detection across a large corpus with quantitative analysis of usage
intensity, agent diversity, and contribution patterns across developer cohorts. The
central finding is that core and peripheral contributors exhibit different patterns
of agent adoption and intensity: agentic development hasn't homogenised contribution
behaviour but instead interacts with the pre-existing structure of open-source
collaboration. This matters for detection methodology directly. Repositories where
agents are used primarily by peripheral contributors may show lower overall signal
density than those where core maintainers adopt agents, meaning adoption rates
measured at the repository level may systematically undercount agent use concentrated
in peripheral contribution channels.

The contributor-level focus is what makes this study worth noting; most prior work
treats adoption as a binary repository-level attribute. The main problem is that
characterising usage patterns requires reliably attributing commits to specific
agents and to contributor roles, so the findings are conditional on the accuracy
of both the detection pipeline and the contributor classification. Khosravani and
Mockus~\cite{khosravani2026} found that single-signal detection misses up to 30 times
the AI activity detected by a full multi-signal approach, implying that many
peripheral-contributor agent uses may be invisible to the detection pipeline rather
than genuinely absent, and the observed role-based usage differences could partly
reflect differential detectability rather than differential adoption.

\section{Developer Interaction with AI Coding Tools}
\label{sec:lr:interaction}
% ------------------------------------------------------------

Understanding why some repositories show agent signals while others do not
requires insight into how developers actually use these tools and how that use
manifests in observable repository artefacts.

\subsection{Bimodal Interaction Patterns}

Barke, James, and Polikarpova~\cite{barke2023} studied how programmers interact
with GitHub Copilot by recruiting 20 participants to perform structured coding
tasks in a controlled laboratory setting with think-aloud protocols. Their approach
used grounded theory analysis of the resulting interaction logs to characterise the
types of prompts used and the cognitive states associated with each. They found a
consistent bimodal pattern: \emph{acceleration mode}, in which developers know what
to write and use Copilot as a speed mechanism (code prompts dominant at 71.4\%),
and \emph{exploration mode}, in which developers are uncertain and use Copilot to
discover APIs or problem structure (comment prompts dominant at 57.2\%). Exploration
interactions took more than twice as long as acceleration ones (248.6 vs.\ 104.7
minutes total), and task familiarity was the main driver of mode.

The theoretically grounded account of human-AI interaction is the study's real
contribution; it moves beyond simple acceptance rates to characterise the cognitive
context of use. 20 participants in a controlled laboratory setting is a small,
unrepresentative sample, though. Ziegler et al.~\cite{ziegler2022} studied 2,631
Copilot users in genuine production contexts and found that acceptance rates varied
in ways that resist clean categorical description, suggesting real developer behaviour
is more continuous and context-dependent than a two-mode model implies. Regardless,
exploration-mode interactions are more likely to leave visible traces in commit diffs
and PR descriptions, since developers write natural-language comments as prompts and
accept large generated blocks; this has direct implications for signal detectability
in this study.

\subsection{Productivity and Acceptance Rates}

Ziegler et al.~\cite{ziegler2022} conducted the largest productivity study of AI
coding tools at the time, matching survey responses from 2,631 GitHub Copilot users
to four weeks of IDE telemetry data collected through an opt-in programme. Their
approach tested multiple productivity proxies (acceptance rate, suggestion volume,
lines accepted) against self-reported productivity ratings. The overall suggestion
acceptance rate was 27\%, with users accepting more than 31 suggestions per active
day on average. Acceptance rate was the strongest single predictor of self-reported
productivity ($r = 0.24$, $p < 0.0001$), though this correlation is weak enough
to indicate that many other factors dominate individual productivity variation.
JavaScript had a higher acceptance rate (30.8\%) than TypeScript (26.3\%), consistent
with TypeScript's stricter type system generating more type-incompatible suggestions
that developers reject.

Scale and objective telemetry data are what set this apart from most work in this
space. The main methodological concern is that the study was conducted by GitHub and
Microsoft employees evaluating their own product. Acceptance rate as a productivity
measure also favours frequent lower-quality suggestions over rare high-quality ones,
and the weak correlation ($r = 0.24$) leaves most productivity variance unexplained.
Self-reported productivity at moderate usage levels may also not capture the quality
degradation that emerges at high adoption intensities: Agarwal et al.~\cite{agarwal2026}
found an 18--39\% post-merge bug rate increase when agents are overused, suggesting
the positive association between acceptance rate and productivity holds only within
a moderate usage range.

\subsection{Pull Request Dynamics and Code Quality}

Mazloomzadeh, Morovati, and Khomh~\cite{mazloomzadeh2026} conducted an empirical
study of how AI coding agents contribute to software development by analysing a
large corpus of agentic pull requests on GitHub. They identified agent-attributed
pull requests and characterised their properties, including code change volume, PR
acceptance outcomes, and types of development tasks. The contribution-level unit of
analysis is the study's strength: it captures the granular properties of how agents
participate in collaborative development workflows rather than treating agent use as
a binary repository-level attribute. The limitation is that it's constrained to
agent-attributed PRs identifiable through explicit markers, which excludes the
majority of AI-assisted contributions. Cynthia et al.~\cite{cynthia2026} found
that explicitly attributed PRs, more common from developers who have opted into
visible agent use, may be systematically different from unattributed contributions
made by peripheral contributors whose use is less prominently signalled.

Ogenrwot and Businge~\cite{ogenrwot2026} studied how AI coding agents modify code
by analysing a large corpus of agent-attributed pull requests from the MSR 2026
Mining Challenge dataset. Their approach characterised the code modification patterns
found in agent-authored pull requests, examining the scope, type, and distribution
of code changes and comparing agent-induced modifications against human-authored
changes on matched repositories. What this work contributes is a characterisation
of what agentic code changes actually look like at the PR level: systematic patterns
in the size and nature of changes agents make relative to human contributors. As
with Mazloomzadeh et al., the restriction to PRs identifiable through explicit markers
is a binding constraint. Khosravani and Mockus~\cite{khosravani2026} found that
explicit markers detect up to 30 times less AI activity than a full multi-signal
approach, so the modification patterns documented here should be interpreted as
those of the most visible tier of agent activity, not a representative cross-section.

Popescu et al.~\cite{popescu2026} investigated autonomous agent contributions in
open-source repositories by tracking activity patterns and code change trajectories
over time across a large corpus of repositories with identifiable agent contributions.
The longitudinal perspective is what distinguishes this study: it reveals temporal
dynamics that cross-sectional snapshots can't capture and provides insight into how
agents are integrated into sustained development activity. The limitation is that
longitudinal attribution depends on reliable signal detection across the full project
history; attribution signals may have changed as agents updated their default
behaviours over the study period, introducing inconsistency into the tracking.
Robbes et al.~\cite{robbesAgenticVery2026} found that adoption in newly created
repositories (71--76\%) far exceeds that in established ones, which suggests agent
activity trajectories should differ substantially between repositories where agents
were adopted early versus those where they were introduced to an already-active
codebase. Studying only the latter likely underrepresents the most agent-intensive
adoption regimes.

Oukhay et al.~\cite{oukhay2026} investigated whether AI-generated commits are
reverted more frequently than human-authored commits by analysing repositories
containing commits attributed to Copilot and Claude Code. Their approach tracked
the downstream history of AI-attributed commits to determine whether they were
subsequently reverted or modified within a defined follow-up window.
Copilot-attributed commits were reverted at 7.6\% and Claude Code-attributed commits
at 7.2\%, compared to 4.7\% for human-authored commits. This is the most direct
empirical measurement of post-merge AI code quality using an objective proxy that
doesn't rely on subjective developer ratings or static analysis metrics. The
observation window is necessarily bounded, though, and some incorrect AI-generated
code may manifest as bugs only after it closes; the reported revert rates likely
understate the true magnitude of the quality difference. Higher revert rates for AI
commits may also reflect their use in riskier task contexts (new features, unfamiliar
codebases) rather than lower intrinsic code quality, conflating task difficulty with
code reliability.

Watanabe et al.~\cite{watanabe2025} studied the use of agentic coding in practice
by empirically analysing pull requests generated by AI coding agents across a corpus
of 157 open-source GitHub repositories. A central finding is that 83.8\% of
Claude Code-generated pull requests were accepted and merged, indicating that
agent-generated contributions meet community quality standards at high rates in
the studied projects. The focus on real-world acceptance outcomes across a diverse
open-source corpus is the main strength: it gives a direct measure of how communities
receive agent contributions in practice. The 157 repositories were selected from
those actively using agentic coding tools, though, which may oversample projects
that have already established positive workflows for reviewing agent contributions;
acceptance rates in the broader population may differ. High acceptance rates may
also partly reflect insufficient scrutiny rather than genuine quality: Oukhay et
al.~\cite{oukhay2026} found that AI-attributed commits are reverted at 7.2--7.6\%
compared to 4.7\% for human-authored commits, suggesting some accepted agent
contributions are subsequently identified as incorrect.

Hora and Robbes~\cite{horaRobbes2026} investigated whether AI coding agents generate
over-mocked tests by comparing mock usage patterns in commits attributed to AI agents
against commits by human authors in the same repositories. Their approach involved
automated classification of test commits by authorship type and automated analysis of
mock library imports and mock object instantiations. They found that AI agents
introduce substantially more mock objects than human-authored commits in the same
codebases, confirming a systematic over-mocking tendency that diverges from the
conventions established by human contributors. The focus on a specific, measurable
test-writing behaviour amenable to automated analysis at scale is what makes this
tractable as empirical work. It's worth noting that the study captures only one
dimension of how agents affect test suites; agents may introduce or omit other
testing patterns such as snapshot tests, integration test boundaries, or coverage
annotations that mock usage analysis doesn't reach. Whether these differences in
mocking practices represent improvements or degradations in test suite quality also
remains an open question.

\section{The JavaScript, TypeScript, and npm Ecosystem}
\label{sec:lr:ecosystem}
% ------------------------------------------------------------

The choice of the JavaScript/TypeScript/npm ecosystem as the focus of this
study is supported by ecosystem scale, tool affinity with AI agents, and a
clear gap in prior empirical work.

\subsection{Ecosystem Scale and Growth}

GitHub, Inc.~\cite{octoverse2025} published the GitHub Octoverse 2025 annual
report, documenting the state of the platform's developer community and language
ecosystem. TypeScript overtook Python as the most widely used language on GitHub
by monthly contributor count for the first time in 2025, reaching 2,636,006 monthly
contributors with a year-on-year growth of 66.6\%. The report attributes a portion
of this growth to AI coding agent adoption, noting that TypeScript's strict typing
and comprehensive IDE tooling make it well-suited for agentic code generation.
Industry reports draw on platform-scale data not accessible to academic researchers,
which is their main value. The methodology is not fully disclosed, though, and the
causal attribution of TypeScript growth to AI tools is asserted rather than
statistically demonstrated. Dakhel et al.~\cite{dakhel2023} found in controlled
experiments that GitHub Copilot increases code production speed but also introduces
more code smells and security vulnerabilities than human-authored code; if
TypeScript's growth were driven primarily by AI quality improvements, those
documented quality trade-offs would impose an adoption ceiling independent of tool
availability.

GitHub, Inc.~\cite{octoverse2024} published the Octoverse 2024 report, providing
an annual snapshot of developer activity and language trends across all of GitHub.
The key finding relevant to this thesis is that JavaScript and TypeScript together
ranked as the two most-used languages on GitHub for the fourth consecutive year, and
npm remained the dominant package registry by new package additions. The 2024 edition
documents the pre-agentic baseline scale and composition of the JS/TS community that
this study's corpus is drawn from. It draws on platform-complete data not accessible
to academic researchers, which contextualises adoption figures. The 2024 report was
compiled before broad access to multiple mature AI coding agents, so it can't account
for the structural shift in repository composition that Robbes et
al.~\cite{robbesAgenticVery2026} document in 2025--2026 data; the pre-agentic
baseline it establishes may underrepresent the full scale of AI agent activity that
was already building by the time the report was published.

Chatzidimitriou et al.~\cite{chatzidimitriou2018} built \emph{npm-miner}, an
infrastructure for measuring software quality properties of the npm registry,
and applied it to a corpus of 598,862 packages. They found that quality metrics
follow heavily skewed distributions driven by the registry's openness, and that the
mean npm package has 4.01 direct dependencies and approximately 1,577 lines of code.
These baselines are the study's contribution: a reference point for the npm ecosystem
that subsequent work can use. The limitation is that it dates from 2018 and predates
the proliferation of AI-generated packages; quality distributions and dependency
patterns in the current npm registry may differ substantially. Robbes et
al.~\cite{robbesAgenticVery2026} find that in 2025--2026 agentic tools are already
detected in 71--76\% of newly created repositories; if AI agents now generate a
substantial fraction of new npm packages, comparisons between the Chatzidimitriou
metrics and any current measurement should be interpreted as capturing a distributional
shift rather than organic evolution of the registry.

\subsection{Ecosystem Affinity with AI Coding Agents}

Galster et al.~\cite{galsterConfig2026} found TypeScript to be the most common
primary language (24.5\%) in repositories with agent configuration files.
Robbes et al.~\cite{robbesAgenticVery2026} found Claude Code to dominate new-project
repositories by a factor of approximately $3\times$ over Copilot, consistent with
its terminal-first design that fits naturally into the npm toolchain.

Dakhel et al.~\cite{dakhel2023} conducted a controlled evaluation of GitHub Copilot
as an AI pair programmer, testing the quality and correctness of Copilot-generated
code relative to human-authored solutions across a structured set of programming
tasks spanning multiple languages including JavaScript. Their approach compared
solutions generated with and without Copilot assistance on standardised benchmarks,
using correctness testing, code smell analysis, and security vulnerability scanning
as quality dimensions. While Copilot increases code production speed, it also
produces more code smells and security vulnerabilities than human-authored code.
The controlled experimental design is what makes this study worth citing: it
directly compares human and AI-assisted solutions on identical tasks across multiple
languages including JavaScript, providing the clearest available causal evidence of
the quality trade-offs associated with Copilot adoption. The limitation is that
standardised task-based exercises don't reflect sustained development in production
codebases; the quality gap observed on benchmarks may not hold at the same ratio in
real-world open-source projects where developers iteratively review and refine
agent-generated code. Barke et al.~\cite{barke2023} documented that experienced
developers selectively apply AI tools in exploration mode for high-uncertainty tasks;
as this selective usage becomes more widespread, the average quality of accepted
AI-generated code would be expected to improve as developers filter out lower-quality
outputs more consistently.

\subsection{GitHub as a Data Source}

Kalliamvakou et al.~\cite{kalliamvakou2016} conducted an in-depth study of the
promises and perils of mining GitHub, analysing 6.8 million public repositories
to characterise the reliability and representativeness of the platform as a data
source for empirical software engineering research. Their approach combined
automated data collection with manual validation on stratified random samples.
They found that 67\% of repositories have only a single committer, the median
project lifespan is 9.9 days, and only 12.5\% were active in the preceding month.
Further, 63.4\% of projects in a random sample were genuine software development
efforts, while the rest were experimental, storage, or academic repositories;
only 10\% of collaborative repositories ever used pull requests, and about 40\%
of PRs that are truly merged appear as non-merged in the GitHub API. This was the
first rigorous characterisation of GitHub data quality issues and directly informed
corpus construction practices in subsequent research. The requirements in this thesis
(at least four stars, at least fifty commits, no forks, creation after February 2025)
implement the recommendations of Kalliamvakou et al.\ for filtering out
non-representative projects.

The study was conducted in 2016, and GitHub usage has changed considerably since
then. The AI-agentic era has arguably intensified precisely the problems
Kalliamvakou et al.\ identified: Robbes et al.~\cite{robbesAgenticVery2026}
document that 71--76\% of newly created repositories in 2025--2026 show signs of
agentic tool use, meaning the fraction of non-representative, short-lived, or
single-author repositories on GitHub has likely grown substantially. The filter
criteria recommended by Kalliamvakou et al.\ are therefore more necessary than
ever, but their specific thresholds may require upward revision in future corpus
construction studies targeting AI-era GitHub data.

Dabi\'c et al.~\cite{dabic2021} introduced the SEART GitHub Search (GHS) tool,
a publicly accessible infrastructure for sampling GitHub repositories with
fine-grained filter combinations, and evaluated how different sampling strategies
affect the properties of the resulting corpus. They found that star-based
stratification produces corpora with more stable and comparable properties across
studies than random sampling or contributor-based stratification. The SEART GHS
tool is widely used in MSR research precisely because it makes corpus construction
reproducible. Its limitation is that it was designed before AI-generated repositories
became a substantial fraction of GitHub content; the star and commit thresholds it
recommends were calibrated on pre-agentic data and may now admit or exclude
AI-generated repositories in ways not anticipated when the tool was evaluated.
Star counts can also be influenced by promotional activity and are not always a
reliable proxy for project quality; corpora filtered by stars may oversample
repositories from well-networked developer communities and undersample equally
active repositories from communities with lower social visibility on the platform.

\section{Geographic Dimensions of AI Coding Agent Adoption}
\label{sec:lr:geography}
% ------------------------------------------------------------

The geographic analysis in this thesis asks which countries show the highest and
lowest AI coding agent adoption rates within the JS/TS/npm ecosystem and whether
differences are statistically significant. The relevant literature covers the
geography of open-source contribution, global patterns in AI tool diffusion, and
country-specific adoption studies.

\subsection{Geographic Distribution of Open-Source Contribution}

Wachs, Nitecki, Schueller, and Polleres~\cite{wachs2022} carried out the
most comprehensive study of geographic patterns in open-source software on GitHub,
analysing contributor location data for millions of repositories combined with
network analysis of collaboration graphs to measure the visibility and reach of
contributions from different countries. Their central finding is that OSS
contribution is heavily concentrated in North America and Western Europe, and there
is a measurable positive relationship between a country's GDP per capita and the
visibility of its developers' GitHub contributions. They also validated GitHub
profile location self-reporting as a practical basis for geographic attribution,
finding that self-reported location is broadly consistent with other geographic
signals for developers who fill in the field, though developers from lower-income
countries are more likely to leave the field blank.

The large scale and the validation of the location inference methodology are the main
contributions: Phase 2 of this thesis's pipeline relies on exactly the kind of
location signal this study characterises. The data collection predates the rise of AI
coding agents, though, so it can't speak to whether the observed geographic
concentration will persist, narrow, or reverse in the agentic era. The study also
measures contribution \emph{visibility} (stars, forks, reach) rather than contribution
volume; visible contributions from the US may reflect the dominance of English-language
documentation and US-based repositories in GitHub discovery mechanisms rather than a
genuine effort gap.

\subsection{Global Diffusion of AI Coding Tools}

Daniotti, Wachs, Feng, and Neffke~\cite{daniotti2025} investigated the global
diffusion and impact of generative AI in software development by analysing over
30 million GitHub commits to measure the share of AI-written code functions by
country and over time. Their approach combined function-level code analysis with
a classifier trained to distinguish AI-generated from human-written Python
functions, then aggregated results by the inferred country of the commit author
using GitHub profile location data. The United States leads adoption with
approximately 29\% of Python functions AI-generated, while countries in South and
South-East Asia, Africa, and Latin America show substantially lower rates. They
also find that experienced programmers benefit more from AI tools, suggesting that
the adoption gap between high-income and lower-income developer communities may
widen over time.

This is the closest existing work to the geographic question addressed in this
thesis. Its main limitations are the focus on Python and the reliance on
function-level AI detection, which captures only a subset of the signals used in
more comprehensive multi-signal detection pipelines and excludes repository-level
signals such as configuration files or PR markers. The geographic ordering observed
for Python may also not translate directly to the JS/TS ecosystem: Robbes et
al.~\cite{robbesAgenticVery2026} find that Claude Code dominates new JS/TS
repositories by a factor of approximately $3\times$ over GitHub Copilot, whereas
Copilot has stronger relative penetration in Python-heavy enterprise settings.
If the agent tool composition differs between ecosystems, the geographic adoption
pattern could differ substantially from the Daniotti et al.\ findings, since the
pattern may be shaped partly by which tools are available through employer licences
versus individual subscriptions. This thesis extends this line of work by applying
a multi-signal detection pipeline to the JS/TS/npm ecosystem and applying formal
statistical tests (chi-squared and pairwise Fisher's exact with false-discovery rate
correction) to test whether country-level differences are statistically significant
rather than merely descriptive.

\subsection{Country-Level Adoption Studies}

Felder, Eisenreich, Fischer, Wagner, and Chen~\cite{felder2026} studied generative
AI adoption in the German software engineering industry through a survey of
109 developers working in regulated environments subject to GDPR and the EU AI Act.
Their approach was a structured questionnaire measuring adoption rates, perceived
productivity effects, and the factors that moderate adoption, with analysis
stratified by organisational size, developer experience, and project context.
Experience level, organisational size, and compliance context all significantly
moderate productivity gains: developers in larger organisations and
less compliance-constrained settings report higher adoption, while those working
under strict data protection constraints report lower willingness to adopt.

The country-specific focus and the explicit attention to the regulatory dimension
are what make this study useful: compliance constraints are invisible in global
aggregate studies and are a plausible explanation for lower adoption in European
contexts. The limitation is that 109 respondents from one country's regulated sector
can't be treated as representative of German developers broadly. The compliance-related
adoption suppression observed in Germany may also not generalise to countries with
less stringent data protection regulation, meaning results from this study could
understate adoption potential in regulatory peers such as France or the Netherlands
and overstate the difference between European and North American developers.

Together, these studies establish that geographic variation in AI coding agent
adoption is real, measurable, and shaped by factors beyond individual developer
preference, including GDP, regulatory environment, and ecosystem-level language
trends. This thesis contributes to this body of work by producing the first
country-level ranking of AI coding agent adoption within the
JavaScript/TypeScript/npm ecosystem at GitHub scale, with Wilson confidence
intervals and formally tested pairwise country comparisons.

\section{Research Gaps}
\label{sec:lr:gaps}
% ------------------------------------------------------------

The review above identifies three research gaps that this thesis addresses.

\textbf{Gap 1: The Ecosystem Scope Gap.}
All major empirical studies of coding agent adoption (Robbes et al.\
\cite{robbesAgenticMuch2026,robbesAgenticVery2026}, Khosravani and Mockus
\cite{khosravani2026}) report rates averaged across all GitHub languages. No
study has measured adoption specifically within the JavaScript/TypeScript/npm
ecosystem, even though configuration file and commit trailer evidence suggests
this ecosystem is among the most active sites of agent adoption~\cite{
galsterConfig2026, octoverse2025}. The aggregate rates provide a reference point
but can't answer whether JS/TS developers adopt more, less, or differently
than the general GitHub population.

\textbf{Gap 2: The Undercounting Gap.}
The 6.46 percentage-point gap between narrow and broad heuristic sets in
Robbes et al.~\cite{robbesAgenticMuch2026}, and the 30$\times$ undercounting
factor documented by Khosravani and Mockus~\cite{khosravani2026}, show that
single-signal detection misrepresents true adoption. No study has quantified
this undercounting delta specifically for the JavaScript/TypeScript ecosystem,
where npm SDK dependency declarations provide an additional signal family not
available in other language ecosystems, and where the high prevalence of Claude
Code use (terminal-first, npm-native) may make the delta larger or smaller than
in cross-language studies.

\textbf{Gap 3: The Geographic Ranking Gap.}
Daniotti et al.~\cite{daniotti2025} and Wachs et al.~\cite{wachs2022} establish
that geographic variation in software development activity and AI tool adoption
exists, but neither produces a ranked country comparison within a specific
ecosystem using a multi-signal detection approach. Daniotti et al.\ focus on
Python and measure AI-written code at the function level; Wachs et al.\ measure
contribution visibility, not tool adoption. No study has ranked countries by AI
coding agent adoption rate within the JavaScript/TypeScript/npm ecosystem, tested
whether the ranking is statistically significant, or reported adoption rates with
confidence intervals at the country level. This thesis fills that gap directly.

Together, these gaps frame the three research questions of this thesis: measuring
adoption within the JS/TS/npm ecosystem (Gap~1), reporting both single-signal and
multi-signal rates to estimate the undercounting delta (Gap~2), and producing a
ranked country comparison of adoption with formal statistical tests (Gap~3).
